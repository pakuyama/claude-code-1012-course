오행 사주 웹앱을 기획부터 GitHub Pages 배포까지

"계획 세워줘"로 시작해 시장 조사, 구현, 배포, 기능 추가, 문서화까지. 웹 서비스 하나를 처음부터 끝까지 완성하는 전체 흐름을 따라갑니다.

  • 소요 시간: 약 2시간

1. 기획: 계획 → 조사 → 요구사항 수정

세 번의 짧은 요청으로 계획서가 점점 단단해졌습니다.

사주 운세 서비스를 만들려고 해 계획을 세워줄래

Claude는 폴더가 비어 있는지 확인한 뒤 MVP 계획을 세웠습니다. 만세력에서 흔히 틀리는 부분(입춘·절입 시각, 진태양시, 서머타임, 야자시)도 미리 짚었습니다.

.env 파일에 firecrawl api키 넣어놨어 이걸 활용해서 계획서 다시써줘

Firecrawl API로 웹 검색 5건, 페이지 스크랩 4건을 해서 시장 규모, 사용자 관심 주제(재물운 58.7%), 경쟁 서비스를 계획서 v2에 반영했습니다.

주의: API 키는 화면에 찍지 않는다

Claude는 .env 내용을 확인할 때도 값을 가렸습니다.

sed 's/=.*/=<hidden>/' .env

키 이름만 확인하고 값은 출력하지 않는 습관을 들이세요.

결과를 알려줄때 신, 정, 경, 병 이런거 말고 그냥 오행만 띄워주고 이에따른 성격분석과 연도별 운세를 재물, 건강, 연애로 나눠서 올리자

여기서 핵심 설계 원칙이 정해졌습니다. 계산은 정확하게, 화면은 쉽게. 내부에서는 천간·지지를 모두 계산하되, 사용자에게는 오행(목·화·토·금·수)과 쉬운 문장만 보여 줍니다.

2. 구현: 빌드 없는 정적 웹앱

깃cli로 배포까지 해줘

Claude는 먼저 환경부터 점검했습니다(git, gh auth status, node). PC에 Node.js가 없었기 때문에 빌드 과정이 필요 없는 순수 HTML/CSS/JS로 결정했습니다.

index.html          화면
css/style.css       스타일
js/saju.js          만세력 계산 (사주 → 오행)
js/interpret.js     성격·연도별 운세 해석
js/app.js           입력·렌더링·공유
vendor/lunar.js     lunar-javascript (MIT)

확인은 로컬 서버와 브라우저 자동화로 했습니다.

python -m http.server 8000

Claude in Chrome으로 페이지를 열어 스크린샷, DOM, 콘솔 오류를 확인했습니다.

3. 배포: gh CLI 세 줄

  1. 비밀 파일 제외: .gitignore에 .env를 넣고 첫 커밋을 합니다.
  2. 저장소 생성과 푸시 
    gh repo create ohaeng-saju --public --source=. --remote=origin --push
  3. Pages 켜기 
    gh api -X POST repos/<사용자>/ohaeng-saju/pages \
  -f "source[branch]=main" -f "source[path]=/"
  4. 빌드 완료 대기: 상태가 built가 될 때까지 확인합니다. 
    gh api repos/<사용자>/ohaeng-saju/pages/builds/latest --jq .status
  5. 배포 검증: 사이트는 200, /.env는 404인지 curl로 확인합니다.
팁: 무료 GitHub Pages는 공개 저장소에서만

무료 계정에서 Pages를 쓰려면 저장소가 public이어야 합니다. 그래서 비밀 파일 제외와 /.env 404 확인이 더 중요합니다.

4. 기능 추가와 캐시 문제

과거에도 무슨일이 있었다도 추가해 볼래?

해석 로직을 "판단 근거 코드 → 현재형/과거형 문장" 구조로 리팩터링해서, 같은 규칙으로 지난 10년 돌아보기를 만들었습니다.

예상 재미로 보는 mbti도 추가해줘 재미이기 때문에 아닐수도 있다는 안내문도 추가해줘

처음 만든 MBTI 추정은 ISTJ가 23%로 쏠렸습니다. Claude는 95,040개 조합을 돌려 분포를 확인했고, E/I를 음양 비율로 바꾸고 오행별 축 배치를 다시 해서 16개 유형이 약 2~12%로 고르게 퍼지게 했습니다.

배포했는데 MBTI 카드가 비어 있다?

MBTI 기능을 배포한 직후 카드가 빈 칸으로 보였습니다. curl -sI로 헤더를 보니 GitHub Pages가 CSS/JS를 10분간 캐시하고 있었습니다. 새 HTML이 이전 JS와 섞여 불러와진 것입니다.

<link rel="stylesheet" href="css/style.css?v=4">
<script src="js/app.js?v=4"></script>

파일 주소 뒤에 버전 쿼리 ?v=를 붙여 해결했고, "CSS/JS를 고치면 숫자를 올릴 것"이라는 규칙을 README에 남겼습니다.

지금까지 한 것을 계획서에 써줘 이미 써져있다면 안써도 돼

마지막으로 진행 내역과 다음 단계를 PLAN.md로 정리해 커밋했습니다.

6. 정리

핵심 요약
  1. 계획 → 조사 → 요구사항 수정 → 구현 순서로 가면 결과물이 흔들리지 않습니다.
  2. API 키는 .env + .gitignore로 관리하고, 배포 후 /.env가 404인지 확인합니다.
  3. gh repo create --push와 gh api .../pages로 배포가 끝납니다.
  4. "배포됨"을 믿지 말고 실제 사이트를 확인하세요. 캐시 문제는 확인 과정에서 발견됐습니다.
  5. 정적 사이트는 ?v= 버전 쿼리로 캐시를 무효화합니다.

확인 퀴즈

Q1. Node.js 없이 웹앱을 만든 방법은?

빌드 도구가 필요 없는 순수 HTML/CSS/JS로 만들고, 라이브러리는 vendor/에 파일로 넣었습니다.

Q2. 배포 직후 새 기능이 안 보였던 이유는?

GitHub Pages가 CSS/JS를 10분간 캐시해서, 새 HTML과 이전 JS가 섞여 불러와졌기 때문입니다.

Q3. MBTI 결과가 한 유형으로 쏠리는지 어떻게 확인했나요?

가능한 입력 조합 95,040개를 모두 돌려 유형별 비율을 확인했습니다.
